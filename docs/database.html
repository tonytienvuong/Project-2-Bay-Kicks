Database

One MongoDB Atlas database, baykicks, with three collections. There is no products.json in the running app — the catalogue is seeded into the database once and read from there after that.

products

Seeded from server/data/products.json by server/seedProducts.js the first time the server starts against an empty collection. 25 documents.

{
  id: 4,                          // the product id used in every URL and cart line
  sku: "EMB-001",
  name: "Embarcadero Knit",
  brand: "Bay Kicks",
  price: 109.99,
  salePrice: 84.99,               // null when the product is not on sale
  sizes: ["7", "8", "9", "10"],
  colors: ["Black", "Bone"],
  quantityInStock: 12,
  ...
}

users

One document per account. Written by POST /api/accounts, read by POST /api/login.

{
  _id: ObjectId("..."),
  login: "tvuong",                // unique, case-insensitive
  email: "tvuong@example.com",    // unique, case-insensitive
  passwordHash: "$2b$10$...",     // bcrypt — the password itself is never stored
  firstName: "Tien",
  lastName: "Vuong",
  phone: "5105551212",
  shippingAddress: { street: "1 Main St", city: "Hayward", state: "CA", zip: "94541" },
  createdAt: ISODate("2026-11-12T...")
}

Uniqueness is enforced twice: a single query checks login and email before the insert, and a unique index on both fields rejects a duplicate that slips through when two signups race (err.code === 11000 is caught and answered as 409).

orders

One document per checkout. This is where the rubric's "reference to the user document" lives: userId holds the MongoDB _id of the user who ordered.

{
  userId: ObjectId("..."),        // reference into users
  orderDate: ISODate("2026-11-12T..."),
  customer: { firstName, lastName, email, phone },
  shippingAddress: { street, city, state, zip },
  billingAddress:  { street, city, state, zip },
  payment: { cardType: "Visa", last4: "4242" },   // never the full number, never the CVV
  items: [
    { productId: 4, name: "Embarcadero Knit", brand: "Bay Kicks",
      size: "10", color: "Black", quantity: 2,
      unitPrice: 84.99, lineTotal: 169.98 }
  ],
  subtotal: 169.98,
  tax: 16.15,                     // 9.5% of the subtotal
  shippingCost: 0,
  total: 186.13,
  status: "Submitted"
}
Prices are re-read at checkout. The session cart remembers the price a line was added at, but POST /api/orders looks every product up again and builds the order from the database's price. A visitor cannot edit a total by editing the request.

What is deliberately not stored

  • The password, in any form other than a bcrypt hash.
  • Card numbers and CVVs — only the card type and the last four digits, for the confirmation page.
  • The cart. It lives in the Express session, so it disappears when the session ends or the server restarts.

Sessions, kept separate from Mongo

express-session uses its default in-memory store. That is a deliberate choice for a class project: nothing to install, and the behaviour is easy to demonstrate (restart the server, the cart is empty). A production shop would put the session store in Mongo or Redis so several instances share it.
