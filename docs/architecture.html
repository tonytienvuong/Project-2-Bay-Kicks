Architecture

Three layers, one deploy: a React bundle in the browser, an Express server on Cloud Run, and MongoDB Atlas outside the container.

The three layers

browser  ──fetch('/api/...')──▶  Express on Cloud Run  ──MongoDB driver──▶  Atlas
React 19                          routes → controllers                 baykicks database
served as static files            sessions in memory                    products, users, orders

1. The browser

The React app is a single page. App.jsx holds which view is showing (home, shop, detail, cart, checkout, account, createAccount) and reads that from the URL pathname on first load. There is no router library: switching views is a state change, so the paths /shop and /cart only matter when the browser first asks for the page.

Every call to the server goes through client/src/api.js — one small function per endpoint, each one a fetch with credentials: 'include' so the session cookie travels with the request.

2. The server

server/app.js wires five things in a deliberate order:

body-parser  →  express-session  →  /api routes  →  express.static(client/dist)  →  index.html fallback

That order is why one URL can serve both halves of the project. A request for /api/products is answered by a controller and never reaches the static handler; a request for /shop matches no file in client/dist, so it falls through to index.html and React draws the shop view.

Inside the API the code is split the way the course teaches it: routes/ maps a URL and method to a function, controllers/ does the work, and middleware/requireLogin.js guards the routes that need a signed-in user.

3. The database

server/db/databaseConnection.js opens one MongoClient when the process starts and hands the same connection to every request. Opening a client inside each controller would create a new connection pool per request and exhaust the free Atlas tier. The pool is closed on SIGINT/SIGTERM, which is what Cloud Run sends when it stops an instance.

One instance, many requests. Cloud Run can run several copies of the Express app at once; each copy has its own connection pool and its own in-memory session store. That is acceptable here — the default session store is fine for a class project and is worth saying out loud in the demo.

What happens on one request

Adding a pair of shoes to the cart, end to end:

  1. ProductDetailView.jsx calls api.addToCart({ productId, size, color, qty }).
  2. The browser sends POST /api/cart with the session cookie.
  3. cartRoutes.js hands it to cartController.addToCart.
  4. The controller looks the product up in the products collection — the price it uses comes from the database, never from the request body.
  5. It finds the matching line by product + size + colour, increments the quantity (capped at the product's stock), and writes the whole cart back to req.session.cart.
  6. It answers { items, count, subtotal }; the nav bar badge and the cart page redraw from that answer.

The same shape applies to checkout: read the session cart, re-price it from products, compute subtotal, 9.5% tax and total, insert one document into orders carrying userId, and only then empty the session cart.
